# Data Model: Deako Hub Simulator

**Branch**: `001-deako-hub-simulator` | **Date**: 2025-10-25 | **Phase**: 1 (Design)  
**Spec**: [spec.md](./spec.md) | **Research**: [research.md](./research.md)

This document defines the core entities and data structures for the Deako Hub Simulator.

---

## Core Entities

### Device

Represents a physical Deako device (light switch/dimmer) managed by the simulated hub.

#### Fields

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| `uuid` | string | Yes | Unique device identifier | Valid UUID v4 format, lowercase |
| `name` | string | Yes | Human-readable device name | Non-empty, max 100 chars |
| `capabilities` | string[] | Yes | Device capabilities | Must contain "power", optionally "dim" |
| `state` | DeviceState | Yes | Current device state | See DeviceState definition below |

#### DeviceState

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| `power` | boolean | Yes | Power state (on/off) | true or false |
| `dim` | integer | Conditional | Dim level percentage | 0-100, required only if "dim" in capabilities, null otherwise |

#### Validation Rules

- UUID must be unique across all devices in configuration
- If device has "dim" capability, it MUST also have "power" capability (FR-005)
- Dim level only meaningful when power is true; when power is false, dim level preserved but not effective
- Device names should be descriptive for test scenario clarity

#### Example

```json
{
  "uuid": "a1b2c3d4-e5f6-4789-a012-b3c4d5e6f789",
  "name": "Kitchen Overhead",
  "capabilities": ["power", "dim"],
  "state": {
    "power": true,
    "dim": 75
  }
}
```

### Message

Represents a protocol message exchanged between client and simulator. All messages are JSON objects with CRLF line termination.

#### Common Fields

All messages share these fields:

| Field | Type | Required | Description | Values |
|-------|------|----------|-------------|--------|
| `name` | string | Yes | Message type identifier | "DEVICE_LIST", "DEVICE_FOUND", "CONTROL", "EVENT", "PING", "DEVICE_POLL" |
| `transactionId` | string | Conditional | Client-provided correlation ID | Required for request messages, echoed in responses |
| `src` | string | No | Source identifier | "client" or device UUID |
| `dst` | string | No | Destination identifier | "hub" or device UUID |
| `status` | string | Conditional | Response status | "ok" or "error" (responses only) |
| `error` | string | Conditional | Error description | Required when status="error" |
| `timestamp` | integer | Yes | Unix timestamp milliseconds | Generated by simulator |
| `data` | object | Conditional | Message-specific payload | See message-specific schemas in contracts/ |

#### Message Types

1. **DEVICE_LIST** (request/response)
   - Request: Client → Hub, queries total device count
   - Response: Hub → Client, returns device count, followed by DEVICE_FOUND stream

2. **DEVICE_FOUND** (server push)
   - Hub → Client, unsolicited device announcement
   - Sent after DEVICE_LIST response and when devices added at runtime

3. **CONTROL** (request/response + event)
   - Request: Client → Hub, changes device state (power/dim)
   - Response: Hub → Client, immediate acknowledgment (~100ms)
   - Event: Hub → All clients, broadcasted state change confirmation (~2s after control)

4. **EVENT** (server push)
   - Hub → Client, unsolicited device state change notification
   - Triggered by: physical button press, HTTP API control, other client control

5. **PING** (request/response)
   - Request: Client → Hub, connection health check
   - Response: Hub → Client, echo with timestamp

6. **DEVICE_POLL** (request/response)
   - Request: Client → Hub, queries specific device current state
   - Response: Hub → Client, returns device state (FR-023: returns status="error" even on success)

#### Validation Rules

- All messages must be valid JSON
- All messages must end with CRLF (`\r\n`)
- Message type ("name") must be recognized
- Required fields must be present
- transactionId required for request messages (DEVICE_LIST, CONTROL, PING, DEVICE_POLL)
- timestamp must be Unix milliseconds (not seconds)

#### Example Messages

**DEVICE_LIST Request:**
```json
{"name": "DEVICE_LIST", "transactionId": "req-001"}
```

**CONTROL Request:**
```json
{
  "name": "CONTROL",
  "transactionId": "ctrl-001",
  "data": {
    "uuid": "a1b2c3d4-e5f6-4789-a012-b3c4d5e6f789",
    "power": true,
    "dim": 75
  }
}
```

**EVENT (State Change):**
```json
{
  "name": "EVENT",
  "timestamp": 1729881234567,
  "data": {
    "uuid": "a1b2c3d4-e5f6-4789-a012-b3c4d5e6f789",
    "name": "Kitchen Overhead",
    "power": true,
    "dim": 75,
    "eventType": "DEVICE_STATE_CHANGE"
  }
}
```

See `contracts/messages.schema.json` for complete JSON Schema definitions.

### Config

Represents simulator configuration loaded from JSON file at startup.

#### Fields

| Field | Type | Required | Description | Default |
|-------|------|----------|-------------|---------|
| `devices` | Device[] | Yes | Array of devices to simulate | N/A |
| `network` | NetworkConfig | No | Network configuration | See NetworkConfig defaults |
| `scenarios` | Scenario[] | No | Named test scenarios | Empty array |
| `log_level` | string | No | Logging verbosity | "INFO" |

#### NetworkConfig

| Field | Type | Required | Description | Default |
|-------|------|----------|-------------|---------|
| `host` | string | No | Bind address | "0.0.0.0" (all interfaces) |
| `port` | integer | No | Telnet port | 23 |
| `http_port` | integer | No | HTTP API port | 8080 |
| `mdns_name` | string | No | mDNS service name | "local-integration" |

#### Scenario

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | Yes | Scenario identifier |
| `description` | string | No | Human-readable description |
| `device_states` | object | Yes | Map of device UUID → DeviceState |

#### Validation Rules

- At least one device required in `devices` array
- Device UUIDs must be unique
- Port must be 1-65535
- HTTP port must differ from telnet port
- log_level must be: "DEBUG", "INFO", "WARNING", "ERROR"
- Scenario device UUIDs must reference existing devices
- Scenario names must be unique

#### Example Configuration

```json
{
  "devices": [
    {
      "uuid": "a1b2c3d4-e5f6-4789-a012-b3c4d5e6f789",
      "name": "Kitchen Overhead",
      "capabilities": ["power", "dim"],
      "state": {"power": false, "dim": 0}
    },
    {
      "uuid": "b2c3d4e5-f6a7-4890-b123-c4d5e6f7a890",
      "name": "Living Room Main",
      "capabilities": ["power"],
      "state": {"power": false, "dim": null}
    }
  ],
  "network": {
    "host": "0.0.0.0",
    "port": 23,
    "http_port": 8080,
    "mdns_name": "local-integration"
  },
  "scenarios": [
    {
      "name": "all-on",
      "description": "All lights powered on at 100%",
      "device_states": {
        "a1b2c3d4-e5f6-4789-a012-b3c4d5e6f789": {"power": true, "dim": 100},
        "b2c3d4e5-f6a7-4890-b123-c4d5e6f7a890": {"power": true, "dim": null}
      }
    }
  ],
  "log_level": "INFO"
}
```

See `contracts/config.schema.json` for complete JSON Schema definition.

## Entity Relationships

```
Config
├── devices: Device[]
│   └── Device
│       └── state: DeviceState
├── scenarios: Scenario[]
│   └── Scenario
│       └── device_states: Map<UUID, DeviceState>
└── network: NetworkConfig

SimulatorState (Runtime)
├── devices: Map<UUID, Device>
├── connections: StreamWriter[]
├── last_command_time: Map<UUID, timestamp>
└── command_queues: Map<UUID, Queue<Message>>
```

## State Transitions

### Device Power State

```
          CONTROL(power=true)
    ┌──────────────────────────────┐
    │                              │
    │                              ▼
OFF ──────────────────────────▶ ON
    │                              │
    │                              │
    └──────────────────────────────┘
          CONTROL(power=false)
```

### Device Dim State (when power=true)

```
DIM(0) ◄─── CONTROL(dim=X) ───► DIM(100)
   │                               │
   └───────── any value ───────────┘
            CONTROL(dim=Y)
```

### Message Flow: CONTROL

```
Client                          Simulator
  │                                 │
  │  CONTROL(uuid, power, dim)      │
  │────────────────────────────────►│
  │                                 │ (validate, update state)
  │  CONTROL(status=ok)             │
  │◄────────────────────────────────│ (~100ms)
  │                                 │
  │  EVENT(DEVICE_STATE_CHANGE)     │
  │◄────────────────────────────────│ (~2s, to all connections)
  │                                 │
```

### Connection States

```
                  connect()
    DISCONNECTED ───────────► CONNECTED
         ▲                         │
         │                         │
         │    close()/error        │
         └─────────────────────────┘
```

For passive rejection (FR-072): only first connection becomes CONNECTED (functional), additional connections remain ACCEPTED but non-functional (zombie).

## Implementation Notes

### Python Type Hints

```python
from dataclasses import dataclass
from typing import Optional

@dataclass
class DeviceState:
    power: bool
    dim: Optional[int] = None

@dataclass
class Device:
    uuid: str
    name: str
    capabilities: list[str]
    state: DeviceState

@dataclass
class Config:
    devices: list[Device]
    network: NetworkConfig
    scenarios: list[Scenario] = None
    log_level: str = "INFO"
```

### JSON Schema Integration

- Load schemas at startup for validation
- Use `jsonschema` library for validation
- Provide detailed validation errors with field paths (FR-043)

### State Management

- Device state stored in-memory only (no persistence)
- State updates are synchronous (single-threaded asyncio)
- EVENT broadcasting is asynchronous (fire-and-forget)
